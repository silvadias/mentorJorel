# 3. PRINCÍPIOS OBRIGATÓRIOS DE ENGENHARIA

## 3.1. SOLID e princípios arquiteturais

Aplique rigorosamente, conforme o contexto:

- **SRP — Single Responsibility Principle:** cada módulo deve ter uma responsabilidade coesa e uma razão clara para mudar.
- **OCP — Open/Closed Principle:** permita evolução por extensão quando isso trouxer benefício real, sem criar abstrações preventivas.
- **LSP — Liskov Substitution Principle:** respeite os contratos comportamentais das abstrações.
- **ISP — Interface Segregation Principle:** priorize contratos pequenos, específicos e orientados às necessidades reais dos consumidores.
- **DIP — Dependency Inversion Principle:** políticas de alto nível não devem depender diretamente de detalhes de infraestrutura.

Dê atenção especial ao ISP e ao DIP.

Considere também:

- DRY: não duplique conhecimento ou regras que deveriam possuir uma única fonte de verdade.
- KISS: prefira a solução mais simples que satisfaça os requisitos.
- YAGNI: não implemente funcionalidades, interfaces ou abstrações sem necessidade demonstrada.
- SoC: separe responsabilidades e preocupações arquiteturais.
- Composição sobre herança.
- CCP — Common Closure Principle: agrupe elementos que mudam juntos.
- ADP — Acyclic Dependencies Principle: mantenha o grafo de dependências acíclico.

Não aplique princípios mecanicamente. Explique conflitos reais entre eles quando existirem e proponha a alternativa mais simples e segura.

## 3.2. Clean Code e nomes

Adote tolerância zero para nomes que ocultem intenção ou reduzam a legibilidade.

Nomes devem revelar claramente:

- O propósito do elemento.
- A responsabilidade que ele possui.
- O conceito de domínio que representa.
- A função que exerce na arquitetura.
- O motivo pelo qual existe.

Para sugestionar nomes Siga rigorosamente:
- Use Intention-Revealing Names — Use nomes que revelem a intenção
- Avoid Disinformation — Evite informações enganosas
- Make Meaningful Distinctions — Faça distinções significativas
- Use Pronounceable Names — Use nomes pronunciáveis
- Use Searchable Names — Use nomes pesquisáveis
- Avoid Encodings — Evite codificações- Hungarian Notation — Notação húngara
- Member Prefixes — Prefixos de membros
- Interfaces and Implementations — Interfaces e implementações

- Avoid Mental Mapping — Evite mapeamento mental
- Class Names — Nomes de classes
- Method Names — Nomes de métodos
- Don’t Be Cute — Não tente ser engraçado com os nomes
- Pick One Word per Concept — Escolha uma palavra por conceito
- Don’t Pun — Não use a mesma palavra para conceitos diferentes
- Use Solution Domain Names — Use nomes do domínio da solução
- Use Problem Domain Names — Use nomes do domínio do problema
- Add Meaningful Context — Adicione contexto significativo
- Don’t Add Gratuitous Context — Não adicione contexto desnecessário

Não utilize abreviações vagas ou desnecessárias.

Exemplos proibidos quando empregados como nomes genéricos:

- `req`
- `res`
- `ctx`
- `mgr`
- `util`
- `data`
- `temp`

Prefira nomes completos e semanticamente precisos, como `request`, `response`, `securityContext` e `accessPolicy`, quando esses nomes realmente representarem os respectivos conceitos.

Uma abreviação só poderá ser utilizada quando for uma convenção inequívoca do domínio ou da tecnologia e sua utilização não prejudicar a compreensão.

Não permita taxonomias duplicadas, nomes redundantes, sinônimos artificiais ou diferentes nomes para o mesmo conceito sem justificativa.

Evite:

- Classes que apenas repassam chamadas sem agregar responsabilidade.
- Interfaces criadas exclusivamente para satisfazer uma regra estética.
- Métodos com responsabilidades heterogêneas.
- Classes genéricas que concentram responsabilidades de vários domínios.
- Arquivos cuja existência não tenha justificativa arquitetural.
- Indireções que tornem o fluxo mais difícil de compreender.
- Refatorações cosméticas sem benefício demonstrável.

### Regra de leitura crítica

Antes de propor uma mudança, avalie se ela melhora efetivamente a compreensão do código, a coesão, o acoplamento, a testabilidade ou a capacidade de evolução.

**Nunca sacrifique a clareza em nome de uma arquitetura aparentemente sofisticada.**

# 4. ARQUITETURA-ALVO

A arquitetura deverá evoluir de forma incremental, respeitando os limites reais do projeto.

Considere os seguintes conceitos como referências arquiteturais.

## 4.1. Domínio

O domínio contém políticas, regras e contratos que representam os conceitos essenciais de sua responsabilidade.

Deve ser independente de:

- Frameworks web.
- Servidores HTTP específicos.
- Bibliotecas de infraestrutura.
- Detalhes de transporte.
- Implementações concretas de armazenamento.
- Mecanismos específicos de autenticação, quando esses mecanismos forem detalhes substituíveis.
- Dependências técnicas que não sejam necessárias ao domínio.

O domínio não deve importar implementações concretas de infraestrutura.

Não introduza entidades, agregados, objetos de valor ou serviços de domínio sem necessidade demonstrada.

## 4.2. Engine

O diretório `engine` deverá representar os contratos puros e os elementos centrais da política de cada domínio arquitetural.

Conforme a responsabilidade identificada, poderá conter:

- Interfaces.
- Tipos.
- Contratos.
- Regras puras.
- Políticas independentes de infraestrutura.

Regra arquitetural pretendida:

**O engine não deve depender de adapters, drivers, servidores, frameworks ou implementações concretas.**

No modelo arquitetural desejado, o `engine` deve ser independente de imports executáveis e de módulos externos.

Quando necessário, avalie separadamente se a implementação de uma regra pura pertence ao `engine` ou a outra parte do domínio. Não presuma que todo código de domínio deva ser colocado em interfaces ou tipos.

Não transforme `engine` em um repositório indiscriminado de arquivos abstratos.

Cada elemento deve possuir uma razão de existir e um contrato compreensível.

## 4.3. Adapter

O diretório `adapter` deverá conter as implementações concretas que conectam contratos abstratos a mecanismos técnicos.

Conforme o contexto, poderá conter:

- Implementações de interfaces.
- Adaptadores para bibliotecas externas.
- Integrações com mecanismos de autenticação.
- Conversões entre modelos externos e modelos internos.
- Implementações de políticas técnicas delegadas pelo domínio.

O adapter pode importar dependências concretas quando isso for necessário para sua função.

Entretanto:

- Não deve concentrar regras de domínio que pertencem ao engine.
- Não deve transformar bibliotecas externas em dependências obrigatórias do domínio.
- Não deve duplicar contratos existentes.
- Não deve assumir responsabilidades de transporte que pertencem a drivers.
- Não deve existir apenas para acrescentar uma camada sem benefício real.

A implementação concreta deve respeitar o contrato que implementa.

## 4.4. Driver

O diretório `driver` deverá conter os mecanismos de entrada e integração que acionam o sistema ou conectam a arquitetura a um ambiente de execução.

Dependendo do projeto, poderá conter:

- Controladores.
- Handlers.
- Middlewares.
- Adaptadores de transporte.
- Integrações específicas com servidores.
- Componentes de entrada que convertem requisições externas em chamadas internas.

Esses elementos devem traduzir o protocolo externo para os contratos internos adequados.

Não devem concentrar políticas de domínio ou duplicar regras de segurança.

A localização exata de cada componente deverá ser decidida após a análise de suas responsabilidades reais.

## 4.5. Direção das dependências

Avalie o seguinte princípio:

`driver → contratos internos ← adapter`

A representação acima é conceitual. O fluxo real de chamadas e a direção das dependências devem ser analisados separadamente.

A implementação concreta deve satisfazer os contratos definidos pelas políticas internas, e não obrigar o domínio a conhecer os detalhes de infraestrutura.

Não permita dependências circulares.

Não crie referências entre camadas apenas para facilitar imports.

A organização dos diretórios deve refletir os limites arquiteturais reais, e não apenas uma preferência visual.

## 4.6. Segurança e independência tecnológica

A camada de segurança deverá ser evoluída para que suas políticas centrais não dependam de um servidor específico.

Analise separadamente:

- Identificação do consumidor.
- Autenticação.
- Autorização.
- Avaliação de API keys.
- Validação de credenciais.
- Aplicação de políticas de acesso.
- Integração com o transporte.
- Adaptação para servidores ou frameworks.
- Configuração e inicialização.
- Tratamento de falhas e respostas externas.

Esses conceitos não devem ser agrupados automaticamente em uma única classe ou módulo.

Determine, com base no código existente, quais responsabilidades pertencem a cada domínio.

Não confunda autenticação com autorização, nem a avaliação de credenciais com a integração HTTP.

O objetivo é tornar a segurança adaptável a diferentes ambientes de execução sem duplicar regras ou introduzir abstrações desnecessárias.
